## この本は「作った後」の本です

GA4 の BigQuery エクスポートを有効にする手順を書いた記事は、日本語でもたくさんあります。
リンクを繋いで、`events_YYYYMMDD` が翌日に生成されるのを確認して、`UNNEST` で `event_params` を開く。
そこまでは、多くの人が半日でたどり着きます。

問題はその先です。

- 半年後、クエリの請求額が想定の 5 倍になっている
- スケジュールクエリが 3 日前から失敗しているのに誰も気づいていない
- ダッシュボードが重すぎて、経営会議の前に開くのをやめた
- 「このテーブル、誰が何のために作ったんでしたっけ」と聞かれて答えられない
- 退職者のアカウントで動いていた転送が止まった

**この本は、これらを起こさないための運用の本です。**
基盤を「作る」話ではなく、**壊さず・安く・再現可能に保つ**話を 25 章にまとめました。

## 対象読者

- GA4 の BigQuery エクスポートを既に有効化していて、SQL も一通り書ける
- ただし「運用」を体系的に整えたことはなく、都度その場しのぎになっている
- 中小 EC・事業会社のデータ担当、または受託でデータ基盤を預かっている人

エクスポートの設定がまだの方は、先に無料記事の
[GA4のBigQueryエクスポート完全設定ガイド](https://zenn.dev/web_benriya/articles/ga4-bigquery-export-setup-guide-2026)
を読んでから戻ってきてください。この本はその続きから始まります。

## 前提とする環境

| 項目 | 前提 |
|---|---|
| GA4 | BigQuery エクスポートが有効（日次またはストリーミング） |
| データセット | `analytics_XXXXXXXXX` が `asia-northeast1` に存在 |
| 権限 | BigQuery の管理者権限（IAM を触る章で必要） |
| 課金 | オンデマンド課金（フラットレートとの比較は第2部で扱います） |

一部の章では Cloud Scheduler / Cloud Functions / Cloud Storage / Terraform / dbt を使います。
どれも章の冒頭で必要なものを明記しているので、使っていないサービスの章は飛ばして構いません。

## 25章の歩き方

6 つの部に分かれています。**頭から順に読む必要はありません。**
いま困っていることから読んでください。

### 第1部 データの入れ方とモデリング（3章）
ストリーミングと日次のどちらを選ぶか、ネストされた GA4 のスキーマをどう扱うか。
後の章すべての土台になるので、時間があればここから読むのを勧めます。

### 第2部 コストを制御する（6章）
**請求額に驚いたことがある人は、まずここです。**
コストを月1万円以下に抑える具体策、キャッシュの挙動、フラットレートとの損益分岐、
`INFORMATION_SCHEMA` での監視、ラベルによる配分、無料枠内で回す設計まで。

### 第3部 自動化とパイプライン（4章）
スケジュールクエリ、サーバーレス ETL、dbt、転送エラーの Slack 通知。
「毎朝勝手に更新されていて、失敗したら気づける」状態を作ります。

### 第4部 高速化（3章）
マテリアライズドビュー、BI Engine、パーティション有効期限。
ダッシュボードが遅い、という苦情への対処です。

### 第5部 品質と復旧（4章）
SQL テスト、データリネージ、タイムトラベルでの復旧、GCS からの再インポート。
**消してしまった後に読むと遅い章**なので、平時に目を通しておいてください。

### 第6部 チーム運用とガバナンス（5章）
IAM 設計、Terraform でのコード管理、エクスポート上限の回避、
スプレッドシートや Cloud Storage への連携。人が増えたときに効いてきます。

## SQL の置き換えルール

本書の SQL は、そのままコピーして 2 箇所を置き換えれば動きます。

| プレースホルダ | 置き換える値 | 例 |
|---|---|---|
| `${PROJECT}` | GCP プロジェクト ID | `my-shop-analytics` |
| `${DATASET}` | GA4 のデータセット | `analytics_123456789` |

一部の章では、これに加えて自社で用意したテーブル（受注データ、広告費など）を参照します。
その場合は章の中で明記しています。

:::message alert
実行する前に、必ずドライランでスキャン量を確認してください。課金されません。

```bash
bq query --dry_run --use_legacy_sql=false '<SQLをここに貼る>'
```

特に `events_*` を `_TABLE_SUFFIX` なしで叩くと、全期間をスキャンして高額になります。
本書の SQL は原則として期間を絞ってありますが、期間の値は自社のデータに合わせて変更してください。
:::

## 収録した SQL について

本書に収録した SQL は、**BigQuery の方言でパース検証を通したもの**です。
記事に書きっぱなしにせず、構文が壊れていないことを機械的に確認しています。

ただし、検証できるのは構文までです。
実際のスキーマはプロパティごとに違います（カスタムディメンションの有無、
`collected_traffic_source` が入っているか、`items` を使っているか）。
**自社のデータで動かして、数字が想定と合うかは必ず確認してください。**
そのための確認手順も、第5部で扱っています。

## 執筆について

本書の執筆には生成 AI を利用しています。
そのうえで、収録した SQL は検証にかけ、構成と説明は筆者が確認したうえで公開しています。
