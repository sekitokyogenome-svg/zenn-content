## はじめに

シリーズ第4回です。前回までで料金と接続の準備が整いました。今回は **Knowledge Catalog** を扱います。

正直に言うと、この回は「早く AI 関数を動かしたい」人には退屈に見えるはずです。しかし**エージェントの回答精度に不満が出たとき、原因の多くはここにあります**。先に構造を理解しておくと、後で無駄に悩まずに済みます。

---

## なぜ精度が上がらないのか

AI エージェントに「先月の売上を教えて」と聞いて、返ってきた数字が社内の認識と違う。これはよくある話です。

原因を考えてみます。エージェントが持っている情報は何でしょうか。

```text
テーブル名: mart_daily_sales
カラム名  : dt, revenue, order_count, channel
```

これだけです。ここから読み取れないことを並べてみます。

- `revenue` は税込みか税抜きか
- 送料は含まれるか
- **キャンセル・返品は差し引かれているか**
- `channel` の値の定義（`organic` に指名検索は含まれるか）
- 自社の「先月」は暦月か、締め日基準か

人間の担当者なら知っていることです。しかしエージェントは知りません。**知らないまま、もっともらしい SQL を書きます。**

これがハルシネーションの正体の相当部分です。モデルの性能が低いのではなく、**判断材料が渡されていない**。テーブル名とカラム名だけ渡された新入社員が、初日に正しい売上集計を書けるはずがないのと同じです。

Knowledge Catalog は、この**業務文脈をエージェントに供給する仕組み**です。

---

## Knowledge Catalog とは何か

Gemini ベースのデータカタログで、構造化・非構造化データから**セマンティクス（意味）を自動抽出し、コンテキストグラフを構築**します。

重要なのは、これが単なるドキュメント置き場ではないことです。

| 従来のデータカタログ | Knowledge Catalog |
|---|---|
| 人間が読むための説明 | **エージェントが参照する文脈** |
| Wiki やスプレッドシートに散在 | データと紐付いて管理される |
| 更新が放置されがち | 自動抽出で追従する部分がある |

そして **MCP 経由でエージェントがこのカタログをツールとして利用できます**。ローカルまたはリモートの MCP サーバーを通じて、エージェントが必要に応じてカタログを引きに行く、という動きになります。

つまり Knowledge Catalog は、**エージェントに対する「社内の正解」の供給源**として機能します。

## 何を書くべきか

自動抽出に任せられる部分もありますが、**業務固有の定義は人間が明示する必要があります**。機械が推測できないからこそ価値があるので、当然です。

優先度の高い順に整理します。

### 優先度1：指標の定義

最も重要です。同じ言葉が組織によって違う意味を持つものを潰します。

```text
売上（revenue）
  税抜き。送料を含まない。
  キャンセル・返品は当月中の発生分のみ差し引く。
  翌月以降の返品は遡って修正しない。

新規顧客
  過去に purchase イベントが1件も存在しないユーザー。
  ゲスト購入は user_pseudo_id で判定するため重複の可能性がある。

アクティブユーザー
  過去28日以内に1回以上セッションを持つユーザー。
  GA4 の「アクティブユーザー」とは定義が異なるので注意。
```

最後の一文のような**「一般的な定義とどう違うか」**を書いておくのが効きます。エージェントは一般的な定義を知っているので、自社が違う場合は明示しないと一般論で答えてしまいます。

### 優先度2：テーブルの使い分け

似たテーブルが複数あると、エージェントは選択を誤ります。

```text
mart_daily_sales
  日次の確定売上。分析にはこれを使う。
  毎朝5時に前日分が確定する。

stg_orders
  中間テーブル。速報値でありキャンセルが反映されていない。
  分析用途では使わないこと。

analytics_XXXXXXXXX.events_*
  GA4の生データ。当日分は未確定で変動する。
```

**「使わないこと」を明記する**のが重要です。存在するテーブルは使ってよいものだ、とエージェントは解釈しがちです。

### 優先度3：カラムの値の意味

コード値は特に危険です。

```text
channel カラムの値
  organic  : 自然検索（指名検索を含む）
  paid     : 運用型広告全般（Google Ads / Meta Ads）
  direct   : 参照元なし（アプリ内ブラウザ経由を含むため過大評価される傾向）
  referral : 外部サイトからの流入

status カラムの値
  0 : 仮注文（分析対象外）
  1 : 確定
  2 : キャンセル
  9 : テスト注文（必ず除外すること）
```

`9 : テスト注文（必ず除外すること）` のような**除外すべきデータ**の情報は、書いていなければ確実に混入します。

### 優先度4：既知の落とし穴

```text
2026年3月以前のデータは計測タグの設定ミリにより
purchase イベントが二重計上されている。
期間比較の際は2026年4月以降を使うこと。
```

これは自動抽出では絶対に出てきません。**組織の記憶に属する情報**です。担当者が変わると失われるので、書いておく価値が最も高い種類の情報でもあります。

## 使ってみる

BigQuery で Knowledge Catalog を利用する準備をします。

```bash
PROJECT_ID=your-project

gcloud services enable dataplex.googleapis.com --project="$PROJECT_ID"
```

そのうえで、テーブルやカラムに説明を付けていきます。既存のテーブルに対しては、BigQuery の description から着手するのが現実的です。

```sql
-- テーブルの説明
ALTER TABLE `your-project.mart.mart_daily_sales`
SET OPTIONS (
  description = '日次の確定売上。税抜き・送料除く。キャンセルは当月発生分のみ控除。毎朝5時に前日分が確定する。速報値が必要な場合も stg_orders は使わないこと。'
);

-- カラムの説明
ALTER TABLE `your-project.mart.mart_daily_sales`
ALTER COLUMN channel
SET OPTIONS (
  description = '流入チャネル。organic=自然検索(指名検索含む), paid=運用型広告, direct=参照元なし(アプリ内ブラウザ経由を含むため過大評価傾向), referral=外部サイト'
);
```

現在の説明を棚卸しするクエリです。

```sql
SELECT
  table_name,
  option_value AS description
FROM `your-project.mart.INFORMATION_SCHEMA.TABLE_OPTIONS`
WHERE option_name = 'description'
ORDER BY table_name;
```

説明が空のテーブルを洗い出します。

```sql
WITH described AS (
  SELECT table_name
  FROM `your-project.mart.INFORMATION_SCHEMA.TABLE_OPTIONS`
  WHERE option_name = 'description'
    AND option_value IS NOT NULL
    AND option_value != '""'
)
SELECT t.table_name
FROM `your-project.mart.INFORMATION_SCHEMA.TABLES` t
LEFT JOIN described d USING (table_name)
WHERE d.table_name IS NULL
ORDER BY t.table_name;
```

**まずこのリストを空にすることを目標にする**と、取り組みが具体的になります。

## 現実的な進め方

全テーブルに完璧な説明を付けるのは、正直しんどい作業です。挫折しないための順序を提案します。

**ステップ1：エージェントに実際に聞いてみる**
まず何も整備せずに、よく聞かれる質問をエージェントに投げます。そして間違えた回答を記録します。

**ステップ2：間違えた原因の文脈だけ書く**
「税込みで計算していた」なら、税の扱いを書く。**全部書こうとしない。**

**ステップ3：もう一度聞く**
直ったか確認します。直っていなければ書き方を調整します。

**ステップ4：繰り返す**

この順序の利点は、**効果が出る箇所から埋まる**ことです。網羅性を目指すと終わりが見えず、しかも誰も読まない説明文が量産されます。実際に間違えた箇所を潰していく方が、投下時間あたりの効果が高くなります。

:::message
整備の優先順位は「**よく聞かれる質問**」×「**間違えると影響が大きい**」で決まります。売上・顧客数のような基幹指標から着手してください。滅多に使わないテーブルの説明を先に書いても効果は薄いです。
:::

## 注意点

**書いた内容が誤っていれば、誤りが増幅されます。**

Knowledge Catalog はエージェントにとっての「正解」になります。定義が古かったり間違っていたりすると、エージェントは自信を持って間違った答えを返します。**説明がない場合より悪化する**ことがあります。

したがって、以下は必須です。

- 定義を変更したら説明も更新する運用にする
- 誰がメンテナンスするかを決めておく
- 定期的に棚卸しする

「一度書いて終わり」にすると、いずれ負債になります。ドキュメント一般の話と同じですが、**エージェントが参照する分だけ影響範囲が広い**ぶん、通常のドキュメントより重要度が高いと考えてください。

## まとめ

- エージェントの回答精度の問題は、**モデルではなく文脈不足**であることが多い
- Knowledge Catalog は**エージェントに業務文脈を供給する仕組み**。MCP 経由で参照される
- 書くべきは**指標の定義 → テーブルの使い分け → 値の意味 → 既知の落とし穴**の順
- **「一般的な定義とどう違うか」「使ってはいけないもの」**を明記するのが効く
- **全部書こうとしない**。間違えた回答を起点に、効く箇所から埋める
- 誤った説明は**誤りを増幅する**。更新運用まで含めて設計する
