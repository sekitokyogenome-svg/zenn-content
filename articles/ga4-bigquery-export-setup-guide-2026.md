## この記事でわかること

- GA4 と BigQuery をリンクして、エクスポートを始めるまでの手順
- 日次とストリーミングの違い、日次エクスポートの上限と停止の条件

## 前提

- GA4 のプロパティで「編集者」以上の権限があること
- リンクに使うメールアドレスが、BigQuery（Google Cloud）プロジェクトの OWNER であること
- 費用はデータ量と使い方で変わります。見積りの考え方は後半の節に書きました
- 所要は設定自体で数分。テーブルが作られるのは翌日以降です

画面名は公式ドキュメントの英語表記（Admin > Product links > BigQuery links）を併記します。日本語UIの細かい文言は変わることがあるため、迷ったら英語表記を手がかりにしてください。

## GA4単体の限界

GA4だけで運用していると、以下の制約にぶつかります。

| 制約 | 内容 |
|------|------|
| サンプリング | 探索レポートで大量データを扱うと、サンプリングされることがある |
| データ保持期間 | GA4側のイベントデータ保持は、標準プロパティで2か月または14か月、GA4 360で最大50か月 |
| 外部データとの結合 | CRMや広告コストデータをGA4内で直接JOINできない |

BigQueryにエクスポートすると、イベント単位の生データに対して SQL で集計でき、外部データとも結合できます。
課金を有効にした通常運用では、BigQuery側のデータは自分で削除しない限り残ります。サンドボックス（無課金）は既定で60日後にテーブル・ビュー・パーティションが失効し、ストレージは生涯上限10GiB（削除しても戻らない）で、ストリーミングは使えません。超えるとエクスポートが失敗しうるため、詳細は「コストの目安」で触れます（出典: [BigQuery サンドボックス](https://docs.cloud.google.com/bigquery/docs/sandbox)）。

## 事前準備：GCPプロジェクトと権限

1. [Google Cloud Console](https://console.cloud.google.com/) にアクセスし、プロジェクトを作成する
2. 請求先アカウントを設定する
3. 「APIとサービス」>「ライブラリ」で BigQuery API を有効にする
4. リンクに使うメールアドレスが、そのプロジェクトの OWNER であることを確認する

リンクを作ると、GA4 側のリンク用の ID に `roles/bigquery.user`（BigQuery ユーザー）が付与されます。組織のポリシーなどで外されると、書き込みに失敗します。リンク後に、プロジェクトの IAM でこのロールが付いているかを確認してください。

:::message
サンドボックス（無課金）でも日次エクスポートはできますが、60日で失効する・ストレージは10GiBまで・ストリーミングは使えない、という制約があります。詳細は「コストの目安」を参照してください。
:::

## BigQueryエクスポートの設定手順

GA4 の管理画面で、プロパティの **「プロダクトのリンク」>「BigQueryのリンク」（Admin > Product links > BigQuery links）** を開き、次の順に進めます。

1. 「リンク（Link）」を押し、「BigQueryプロジェクトを選択（Choose a BigQuery project）」で、先ほどのプロジェクトを選んで確認する
2. データのロケーションを選んで「次へ」
3. 「データストリームとイベントを設定（Configure data streams and events）」で、エクスポートに含めるストリームと、**除外する**イベントを選ぶ
4. モバイルアプリのストリームがある場合は、「広告IDを含める（Include advertising identifiers for mobile app streams）」を必要に応じて選ぶ
5. エクスポート頻度を「毎日（Daily）」「ストリーミング（Streaming）」から選ぶ（両方も可）
6. 内容を確認して「送信（Submit）」

イベントは「選んで入れる」形ではなく、既定ではすべて含め、不要なものを除外する形です。除外は後から「データストリームとイベントを表示」で変更できます。

### ロケーションの選び方

日本国内向けのサイトなら、`asia-northeast1`（東京）を推奨します。クエリで他のデータセットと結合するとき、同じロケーションにそろえておく必要があるためです。

:::message alert
ロケーションを後から変えることはできますが、手間がかかります。リンクを削除し、データセットを作り直して再リンクする流れで、その間のデータは欠損します。クロスリージョンのデータセットレプリケーションを使えば、欠損なしで移せる場合があります。組織のポリシーで米国への保存が禁止されている場合は、別のロケーションを選びます。
:::

## エクスポート方式の比較：日次 vs ストリーミング

| 項目 | 日次（Daily） | ストリーミング（Streaming） |
|------|---------------|---------------------------|
| データ反映 | 前日分が日次テーブルとして作成される | 当日分が随時反映される |
| テーブル名 | `events_YYYYMMDD` | `events_intraday_YYYYMMDD` |
| 件数の上限 | 標準プロパティは1日100万イベント | 上限なし |
| 追加コスト | GA4側の追加料金なし（BigQueryの保存・クエリ費用のみ） | $0.05/GB（GA4ヘルプの表記。目安は約60万イベント/GB） |
| 注意点 | 上限超過が続くと一時停止する | 新規ユーザー・新規セッションの流入元が含まれない（[GA4ヘルプ](https://support.google.com/analytics/answer/9358801)） |

GA4 360 には、これに加えて Fresh Daily があります。通常は午前5時頃までにデータが届き、その後も60分以内の間隔で更新されます。

ストリーミングのテーブルには、新規ユーザー・新規セッションの流入元が含まれません。流入元の分析には、日次テーブルを使ってください。

:::message
まずは日次エクスポートだけで始めるのが無難です。リアルタイム分析の要件が出てから、ストリーミングを追加します。ただし日次にも「1日100万イベント」の上限があり、超えると止まります（次節）。
:::

## 日次エクスポートの上限と停止

標準プロパティの日次エクスポートは、**1日100万イベントが上限**です。超過が続くと、日次エクスポートは一時停止されます。停止中の日の分は、再開後も再処理されません。上限を大きく超えている場合は、すぐに停止されることもあります。

- 超過すると、プロパティの管理者・編集者にメールで通知される
- 対策は、除外するストリームやイベントを増やし、1日の件数を減らすこと
- GA4 360 は、公式ページ上でイベント数の上限が示されています（日次エクスポートで1日あたり最大200億イベント）
- ストリーミングには件数の上限がない

設定後に、日ごとのイベント数を確認する習慣をつけてください。停止は気づきにくく、抜けた日は戻せません。

## エクスポートされるデータの構造

日次エクスポートでは、`events_YYYYMMDD` という日次テーブルが作られます。
遅れて届いたイベントがあるため、日次テーブルは数日間更新されます（スキーマの公式ページでは、イベント日から最大3日）。直近の数日分は、値が変わりうるものとして扱ってください。

各行が1つの**イベント**に対応し、パラメータはネスト（RECORD型）で格納されます。

| カラム名 | 型 | 内容 |
|----------|-----|------|
| `event_date` | STRING | イベント発生日（YYYYMMDD形式） |
| `event_name` | STRING | イベント名（`page_view`, `purchase` など） |
| `event_params` | RECORD（繰り返し） | イベントパラメータのキー・値ペア |
| `user_pseudo_id` | STRING | Cookieベースのユーザー識別子 |
| `collected_traffic_source` | RECORD | イベントに付いていた流入元情報（manual_medium, manual_source など） |
| `session_traffic_source_last_click` | RECORD | セッション単位のラストクリックの流入元 |
| `device` | RECORD | デバイス情報 |
| `geo` | RECORD | 地域情報 |

### セッションIDを取得するクエリ

`ga_session_id` は `event_params` 内にネストされているため、`UNNEST` で展開して取得します。

> SQL の動作確認: 以下の SQL は、架空のダミーデータ（GA4 のエクスポート形式を模したもの）でエラーなく実行できました。実際の GA4 エクスポートでの検証は行っていません。

```sql
-- page_view イベントのセッションIDを取り出す
SELECT
  user_pseudo_id,
  (SELECT value.int_value FROM UNNEST(event_params) WHERE key = 'ga_session_id') AS session_id,
  event_name,
  event_timestamp
FROM
  `project_id.analytics_XXXXXXX.events_20260328`
WHERE
  event_name = 'page_view'
LIMIT 100
```

### 流入元（メディア）を取得するクエリ

`collected_traffic_source` は、イベントに付いていた流入元の値をそのまま持ちます。

```sql
-- session_start イベントの流入元（medium / source）ごとの件数
SELECT
  collected_traffic_source.manual_medium AS medium,
  collected_traffic_source.manual_source AS source,
  COUNT(*) AS event_count
FROM
  `project_id.analytics_XXXXXXX.events_20260328`
WHERE
  event_name = 'session_start'
GROUP BY
  medium, source
ORDER BY
  event_count DESC
```

セッション単位で、GA4 のレポートに近い流入元を見たいときは、`session_traffic_source_last_click` も使えます。Google 広告など、広告系の流入元の項目も含まれます。

:::message alert
`traffic_source.medium` を使うと、セッション単位ではなく、ユーザーを最初に獲得した流入元が返ります。セッション単位の流入元は、上記の `collected_traffic_source` か `session_traffic_source_last_click` を使います。
:::

## コストの目安

BigQueryの料金は、主に**保存**と**クエリ**の2つです。単位は GB・TB ではなく **GiB・TiB** です。

| 項目 | US マルチリージョンの単価 |
|------|---------------|
| アクティブストレージ | $0.02/GiB/月 |
| 長期ストレージ（90日以上未編集） | $0.01/GiB/月 |
| オンデマンドクエリ | $6.25/TiB（スキャン量課金） |
| 毎月の無料枠 | 保存 10GiB + クエリ 1TiB |

上の単価は US マルチリージョンの値です。東京（`asia-northeast1`）は単価が異なります。[公式価格ページ](https://cloud.google.com/bigquery/pricing)で確認してください。

月額の見積りは、次の考え方で出せます。

- 保存: 1イベントの平均サイズ × 1日の件数 × 保存日数 × 保存の単価
- クエリ: 1回にスキャンする量 × 月の実行回数 × クエリの単価（日付で絞ると、スキャン量が減る）
- 平均サイズは、実際にエクスポートされたテーブルのサイズ ÷ 行数で測れます

**無課金（サンドボックス）で運用する場合の注意**: サンドボックスでは、テーブル・ビュー・パーティションが既定で60日後に自動失効します。ストレージは生涯上限10GiB（削除しても戻らない）で、超えるとエクスポートが失敗しうるほか、ストリーミング（intraday）も使えません。冒頭の「残る」は、課金を有効にした通常運用の話です。これらは GA4 側の保持期間（標準2か月または14か月）とは別物です。

:::message
コスト最適化には、パーティション分割や日付での絞り込み、スロット予約（定額制）があります。まずはオンデマンドで始め、実際の使用量を見てから判断します。
:::

## よくあるハマりどころ

### 1. リージョンの選択ミス

誤ったロケーションで作ってしまったら、リンクを削除し、データセットを作り直して再リンクします。その間のデータは欠損します。データの移行も手作業になるため、最初に決めておくのが楽です。

### 2. エクスポートが動いているか確認しない

設定後、テーブルが作られるまでに最大24時間かかります。翌日に BigQuery コンソールでデータセットとテーブルを確認してください。

```bash
# データセット内のテーブルを一覧する
bq ls --max_results=10 project_id:analytics_XXXXXXX
```

### 3. intraday テーブルの扱い

`events_intraday_YYYYMMDD` は、その日の `events_YYYYMMDD` が完成すると削除されます。intraday のデータを残したい場合は、別テーブルにコピーする仕組みが必要です。

### 4. 日次エクスポートの上限

前述のとおり、標準プロパティは1日100万イベントを超えると、日次エクスポートが一時停止します。停止中の日は再処理されないため、早めにイベントの除外を検討してください。

## まとめ

- 先に権限（GA4 は編集者以上、BigQuery は OWNER）を確認し、ロケーションは `asia-northeast1` を推奨する
- 日次エクスポートから始め、1日100万イベントの上限と停止に注意する
- 翌日にテーブルの生成を確認し、`UNNEST` でネスト構造を展開して分析を始める

BigQueryへのエクスポートが完了したら、次はデータを効率的に管理・活用するためのレイヤー設計が重要です。以下の記事で、BigQuery上に3層構造（raw / staging / mart）を構築する方法を解説しています。
